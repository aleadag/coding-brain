# v0.59.0 Release Design

## Context

Coding Brain is ready to prepare a release from the current `origin/main` after
the merged shell-safety review. The root package is still versioned `0.58.0`,
the internal crates are versioned `0.53.0`, and the current user-facing changes
remain under `[Unreleased]`. The existing `0.58.0` changelog section is already
dated but was never tagged; the latest actual release tag is `v0.57.2`. This
coordinated release will therefore use `0.59.0` and cover the full
`v0.57.2...v0.59.0` range in its release notes.

The release deliberately precedes fixes for `codexctl-zz0cx`,
`codexctl-6boi`, and `codexctl-478t`. Those issues remain tracked; this release
must not weaken or bypass a quality or security gate to accommodate them.

## Goals

- Publish `coding-brain`, `coding-brain-core`, and `coding-brain-tui` at
  version `0.59.0`.
- Preserve the existing tag-driven crates.io, GitHub Release, and Homebrew
  distribution flow.
- Make package metadata and tag validation correct for all three crates.
- Make every crate publication retry-safe after a partial external success.
- Keep GitHub workflow permissions and external credentials narrowly scoped.
- Release only the exact reviewed commit merged through a release PR.

## Non-Goals

- Fix any currently open product or test issue.
- Change the release archive format, supported targets, installer behavior, or
  single-executable `cbrain` decision.
- Publish from an unmerged release branch or create a tag before fresh gates
  pass.

## Release Changes

Create an isolated `release/v0.59.0` worktree from current `origin/main`. Do not
touch the existing untracked research file in the primary checkout.

The release PR will:

- set all three package versions to `0.59.0`;
- update internal dependency constraints and `Cargo.lock` consistently;
- move the current `[Unreleased]` entries into
  `[0.59.0] - 2026-08-03` and create a fresh empty `[Unreleased]` section;
- add a concrete `v0.59.0` release-notes body covering
  `v0.57.2...v0.59.0`, to be prepended to GitHub's generated notes;
- change the core and TUI crate repository metadata from
  `aleadag/codexctl` to `aleadag/coding-brain`;
- retain crates.io publishing and every supported `cargo install` instruction;
- extend the tag/version check to require the root, core, and TUI versions to
  equal the tag; and
- preflight the first workflow attempt so any pre-existing `0.59.0` package
  stops publication, while reruns give all three publication jobs an
  exact-version already-published guard.

The workflow will default to `contents: read`; only the GitHub Release job will
receive `contents: write`. Cargo and Homebrew tokens will be limited to the
steps that require them, checked for presence without printing them, and never
written to logs.

The workflow will continue publishing in dependency order:

1. build release archives;
2. publish `coding-brain-core`;
3. wait up to ten minutes for Cargo to resolve the exact published core
   version, then publish `coding-brain-tui`;
4. wait up to ten minutes for Cargo to resolve the exact published TUI
   version, then publish `coding-brain`;
5. create the GitHub Release and upload four platform archives and checksums;
6. update the Homebrew formula.

## Verification

Before opening the release PR, run:

- `cargo fmt --all -- --check`;
- `cargo clippy --all-targets -- -D warnings`;
- `cargo test --all-targets`;
- `cargo build`;
- the Nix package checks;
- package-content checks for all three crates; and
- every crates.io dry-run possible before the dependency crates exist in the
  public index.

Run the gates without test exclusions, production-timeout changes, or other
weakening. If `codexctl-478t` reproduces, retain its log and confirm that it
matches the documented scheduler-sensitive signature. A release still requires
a subsequent clean full run and a completely green exact-head GitHub check
suite. Any novel or unclassified failure blocks the release.

Before tagging, confirm that the Cargo and Homebrew secret names exist, the
three crate names remain available or correctly owned, and the Homebrew tap is
reachable. The tag workflow must fail early if a required secret is empty.

Add or update release-workflow tests so the repository enforces aligned tag
versions and retry-safe root publication. Request an independent review of the
exact release diff. The release PR must pass its complete GitHub check suite.

After merge, fetch `origin/main`, identify the exact resulting commit regardless
of merge strategy, verify that its tree matches the reviewed release tree and
that its required checks are green, and confirm that `v0.59.0` is absent both
locally and remotely. Present that exact SHA for a final go/no-go. Create the
annotated `v0.59.0` tag only on that commit, then verify that the remote tag
resolves to it.

After pushing the tag, monitor the entire release workflow and independently
verify:

- all three crates exist at `0.59.0` on crates.io;
- the GitHub Release contains four archives and four matching checksum assets;
- every checksum validates, each archive contains only the expected `cbrain`
  executable, and each binary reports version `0.59.0`; and
- the Homebrew formula points to `v0.59.0` with the published checksums.

## Failure Handling

Any failure before the tag is pushed stops the release. Do not skip, weaken, or
reinterpret a failed gate as success.

Crates.io versions are immutable. If the tag workflow fails after one or more
crates are accepted, keep `v0.59.0` and recover forward. Publication jobs must
recognize already-published `0.59.0` crates so rerunning the workflow can
continue without duplicate-publication failure. Do not delete and recreate the
tag to conceal or work around a partial release.

Use this recovery policy:

- rerun the same tag workflow after a transient infrastructure or credential
  failure;
- if a deterministic source defect is found before publication, stop, fix it
  on `main`, and release `0.59.1` rather than moving or reusing `v0.59.0`;
- complete a partial but safe crates.io publication forward at `0.59.0`;
- if a published crate is unsafe or security-defective, yank only the affected
  version, disclose the reason, and release `0.59.1`; and
- repair and rerun only the tap update after a Homebrew-only failure.

Record any recovery work as a Beads follow-up.

## Known-Issue Disclosure

The explicit GitHub release-notes body will briefly disclose the tracked false
lifecycle diagnostic (`codexctl-6boi`) and conservative `time -o` false denial
(`codexctl-zz0cx`). Neither is represented as fixed in `0.59.0`. The internal
scheduler-sensitive test flake (`codexctl-478t`) remains tracked as release-gate
evidence but is not presented as a shipped runtime limitation.

## Success Criteria

- The release PR contains only approved release-critical files and passes all
  local and GitHub gates.
- The annotated tag points to the exact reviewed merge commit.
- All three crates, the GitHub assets and checksums, and the Homebrew formula
  publish successfully at `0.59.0`.
- The repository is left with a fresh `[Unreleased]` section and the three
  deferred issues remain open for follow-up.

## Stress Test Results: v0.59.0 Coordinated Release

Stress-tested on 2026-08-03 across nine release branches. All nine recommended
boundaries were accepted without unresolved objections.

### Resolved Decisions

- Release risk: proceed only after fresh gates; disclose the two user-visible
  limitations but not the internal scheduler-sensitive test flake.
- Publication: align all packages at `0.59.0`, publish in dependency order, and
  require Cargo-visible exact versions before publishing downstream packages.
- Immutability: reject pre-existing versions on the first attempt, make reruns
  idempotent, and never move or reuse the release tag.
- Provenance: tag the exact checked merge commit only after a final go/no-go.
- Verification: require an unweakened clean run and green exact-head CI, plus
  independent checks of every published distribution channel.
- Security: use least-privilege GitHub permissions and narrowly scoped secrets.
- Recovery: distinguish transient, partial-safe, unsafe, and Homebrew-only
  failures and recover forward according to their blast radius.

### Changes Made

- Corrected the release comparison base to the latest real tag, `v0.57.2`.
- Added an explicit release-notes artifact and disclosure boundary.
- Replaced API-only propagation checks with bounded Cargo-resolution checks.
- Added first-attempt collision checks, all-crate rerun guards, credential
  preflights, least-privilege permissions, and a detailed recovery matrix.

### Deferred / Parking Lot

- `codexctl-zz0cx`, `codexctl-6boi`, and `codexctl-478t` remain separate
  post-release work and are not silently included in this release PR.

### Confidence Assessment

- Overall: High.
- Areas of concern: crates.io and Homebrew are external immutable or
  independently authenticated systems, so their propagation and credentials
  still require live verification during release execution.

The single reflexion pass found no skipped mapped branch, rubber-stamped risk,
or new unhandled failure mode. The design now covers architecture and
alternatives, assumptions, dependencies, edge cases, scale through bounded
polling, failure modes, and the mandatory security and risk branch.
