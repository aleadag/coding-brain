# Research: v0.59.0 Release Workflow Contracts

> **Date:** 2026-08-03
> **Bead:** codexctl-kiwx9.1
> **Status:** Complete

## Summary

`softprops/action-gh-release` can prepend a checked-in release body to GitHub's
generated notes, and only that job needs `contents: write`. Cargo publication
readiness must be checked through Cargo rather than inferred from the crates.io
web API: use an exact-version `cargo info` lookup as a bounded readiness signal,
then require a downstream `cargo publish --dry-run` before the real upload.

## Key Findings

### A Checked-In Body Is Prepended to Generated Notes

> **Confidence:** high — independently verified against the pinned v2.6.2
> implementation and GitHub's official release API contract.

For `softprops/action-gh-release` v2.6.2, `body_path` is read as the effective
release body. When `generate_release_notes` is true and that body is non-empty,
the action places the explicit body first and the generated notes after it,
separated by two newlines. [S1] [S2] [S3]

The stable contract is that the explicit body is prepended. The exact two-line
separator is implementation behavior in v2.6.2 rather than a separate GitHub
platform guarantee. [S1] [S3]

### Release Creation Alone Needs Contents Write

> **Confidence:** high — independently verified against GitHub workflow and
> REST API documentation.

GitHub permits job-specific `GITHUB_TOKEN` permissions. Checkout and build jobs
can retain `contents: read`; the job that creates the release needs
`contents: write`. No discussion permission is needed because this workflow
does not create a discussion. [S3] [S4]

### Publication Success and Index Visibility Are Different Events

> **Confidence:** high — official Cargo registry and publish documentation
> explicitly distinguish the registry index from the web API.

A Cargo registry contains an index used to find crates and may separately
provide a web API for publication. The registry may acknowledge a successful
publish before the new version appears in its index, and Cargo itself polls the
index after upload. Therefore an exact crates.io API response is not sufficient
as the downstream-publication gate. [S5] [S6] [S7]

### Use a Two-Stage Cargo Gate

> **Confidence:** high for the dry-run gate; medium for `cargo info` as a
> readiness signal because Cargo does not document it as a formal downstream
> resolver contract.

`cargo info 'crate@exact-version' --registry crates-io` is an official
exact-version registry lookup and reads information from the package's
`Cargo.toml`. The explicit registry prevents Cargo from preferring a matching
local workspace package; a fresh task-specific `CARGO_HOME` removes existing
Cargo index and package caches. A successful online run is therefore evidence
that Cargo obtained the registry/package data during that run, but Cargo does
not document this command as a formal network or downstream-resolution
contract. Treat success only as a readiness signal. [S8] [S12]

After that signal, run exactly one downstream
`cargo publish --dry-run -p <package> --locked --registry crates-io`. Cargo
documents that dry-run performs the publication checks without uploading;
packaging normalizes the manifest, removes path selection in favor of the
versioned dependency, and rebuilds the distributable archive from a pristine
state. A dry-run failure is a hard release failure, not another propagation
retry. [S7] [S9] [S10]

The ten-minute retry bound and ten-second interval are project release policy,
not a crates.io service-level guarantee.

### The Action Major Tag Is Mutable

> **Confidence:** high — the GitHub refs API showed `v2` resolving to v2.6.2 at
> commit `3bb12739c298aeb8a4eeaf626c5b8d85266b0e65` on 2026-08-03.

`softprops/action-gh-release@v2` is a moving major tag. Pinning release actions
to immutable commit SHAs would reduce supply-chain drift, but the repository
currently uses version tags throughout the workflow. A repository-wide pinning
change is separate hardening work and should not be silently added to the
version-release diff. [S11]

## Codebase Context

- `.github/workflows/release.yml` currently grants `contents: write` globally,
  uses API-only propagation waits, lacks an already-published guard for the root
  crate, and generates notes without `body_path`.
- `tests/release_workflow.rs` currently enforces only the quality-suite ordering
  and archive naming contract.
- The workflow already publishes core, TUI, and root in dependency order, so the
  release change can harden the existing sequence without redesigning it.

## Recommendations

1. Add a checked-in `.github/releases/v0.59.0.md` and pass it as `body_path`
   while retaining `generate_release_notes: true`.
2. Default the workflow to `contents: read` and grant `contents: write` only to
   the release-creation job.
3. Replace API-only downstream waits with a bounded exact-version `cargo info`
   signal using an isolated task-specific Cargo cache, followed by a single
   downstream `cargo publish --dry-run`.
4. Keep API exact-version checks only for collision detection and idempotent
   reruns, where publication existence—not Cargo resolution—is the question.
5. Track immutable action pinning separately from `v0.59.0`.

## Recommended Beads

- Create a post-release hardening bead to pin release-workflow actions to
  reviewed immutable commit SHAs; classify it from a dedicated workflow-wide
  audit rather than expanding this release PR opportunistically.

## Open Questions

None for the `v0.59.0` plan. Live credential validity, current crate ownership,
and external propagation still require pre-tag and post-tag verification.

## Refuted / Discarded Claims

- Discarded: “A successful `cargo info` proves the downstream dependency graph
  resolves.” Official documentation supports exact-version lookup and package
  metadata retrieval, but not that broader resolver claim. The downstream
  `cargo publish --dry-run` is the authoritative gate.
- Discarded: “A successful crates.io API lookup proves Cargo can consume the
  package.” Cargo documents that API acknowledgement may precede index
  visibility.
